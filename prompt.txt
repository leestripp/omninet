## Bug #1: HEAD requests not matching GET routes

**Date:** 2026-05-12
**Status:** ✅ FIXED
**Component:** Router / HttpServer

### Description
HEAD requests were not matching GET routes in the router. When a GET handler was registered for a path, a HEAD request to the same path returned 404 Not Found.

### Root Cause
The router's `match()` method only matched exact HTTP methods. HEAD requests fell through to the catch-all which returned 404.

### Fix Applied
OmniNet team added logic in `Router::match()` to treat HEAD requests as GET requests if no explicit HEAD route exists.

### Verification
- `curl -I http://localhost:4242/` → 200 OK with headers
- `curl -I -X HEAD http://localhost:4242/` → 200 OK with headers
- Both routes now return security headers

## Bug #4: Catch-all route not matching (CRITICAL - Security)

**Date:** 2026-05-12
**Updated:** 2026-05-12
**Severity:** HIGH (Security Concern)
**Status:** ✅ FIXED
**Component:** StaticHandler

### Issue Summary

Requests to paths like `/.env`, `/.config`, `/.git/config` were returning HTTP 200 with empty body instead of 404.

### Root Cause

The `StaticHandler::handle()` method was returning `false` for hidden files (files starting with `.`) but NOT setting the response to 404 before returning. This left the response in its default state (200 OK, empty body).

### Fix Applied

Modified `src/http/StaticHandler.cpp` to set `resp = Response::notFound()` in these cases:
1. When `isHidden(path)` returns true (line 85-88)
2. When a directory has no index file and directory listing is disabled (line 112-116)
3. When path does not exist or is not accessible (line 123-125)

### Verification
- `GET /.env` → 404 Not Found ✅
- `GET /.config` → 404 Not Found ✅  
- `GET /.git/config` → 404 Not Found ✅
- `GET /index.html` → 200 OK with content ✅
- All 110 unit tests pass ✅

### Security Impact

This is a SECURITY ISSUE because:
- Requests to `/.env`, `/.config`, `/.git/config` return 200 instead of 404
- While no sensitive data is leaked (empty body), returning 200 for non-existent files is:
  - Misleading for debugging
  - Potentially exploitable in certain scenarios
  - Against HTTP specification (404 should mean "not found")

### Test Results

| Path | Expected | Actual (Before Fix) | Actual (After acc5a68) |
|------|----------|---------------------|------------------------|
| `/.env` | 404 | 200 (empty) | 200 (empty) |
| `/.config` | 404 | 200 (empty) | 200 (empty) |
| `/.git/config` | 404 | 200 (empty) | 200 (empty) |
| `/nonexistent` | 404 | 404 ✅ | 404 ✅ |
| `/static/file.txt` | 200 | 200 ✅ | 200 ✅ |

### Root Cause Analysis

#### Hypothesis 1: Route Ordering
The `/*` catch-all should be last in route registration order, but something in the route matching logic may be exiting early.

```cpp
// Route registration order in lscppdev.com:
router.get("/static/*", staticHandler);    // Line 496
router.get("/images/*", imagesHandler);   // Line 522
router.get("/downloads/*", downloadsHandler); // Line 549
router.get("/robots.txt", robotsHandler);  // Line 577
router.get("/*", catchAllHandler);        // Line 590 - SHOULD catch everything else
```

When request `/.env` comes in:
1. Check `/static/*` - NO MATCH (path is `/.env`)
2. Check `/images/*` - NO MATCH
3. Check `/downloads/*` - NO MATCH
4. Check `/robots.txt` - NO MATCH
5. Check `/*` - **Should match but returns 200 instead**

#### Hypothesis 2: Regex Transformation of `/*`

The pattern `/*` is transformed to regex. If the regex transformation is flawed, it may not properly match all remaining paths.

#### Hypothesis 3: Handler Response Not Set

Even when `/*` matches, the response may not have a status/body set properly. The fix in acc5a68 attempts to address this by checking `bodySize() == 0`, but it's not working for `/.env`.
